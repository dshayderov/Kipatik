# Руководство администратора Kipatik

Документ описывает всё, что может сделать администратор платформы: получить доступ к панели, управлять пользователями, ролями и проектами, включать и выгружать модели анализа кода, настраивать лимиты хранилища, разворачивать систему и разбирать её сбои.

Для кого он написан: системный администратор, отвечающий за развёртывание и эксплуатацию Kipatik, и администратор проекта, которому поручили управлять учётными записями и настройками.

Как соотносятся два руководства:

- **Руководство пользователя** описывает ежедневную работу в системе: доска, задачи, комментарии, подключение репозитория, приглашения в проект.
- **Руководство администратора** (этот документ) описывает всё, что снаружи рабочего места пользователя: учётные записи, роли и права, модели, хранилище, развёртывание и диагностику.

Граница проходит по признаку «суперпользователь»: только он видит панель администратора. Всё, что внутри проекта, описано в руководстве пользователя.

> **Осторожно: пароль по умолчанию.** При первом старте сервера создаётся
> учётная запись `admin@example.com` с паролем `admin` и правами администратора.
> Смените пароль сразу после первого входа. Подробности — в разделе 9.3.

## 1. Получение прав администратора

Права администратора — это признак «суперпользователь» у учётной записи. Он не выдаётся при регистрации и не настраивается в профиле: по умолчанию у нового пользователя его нет, поэтому выдать права может только тот, кто их уже имеет.

Способы получить доступ:

1. **Войти под учётной записью, созданной при первом старте сервера** (`admin@example.com` / `admin`) — единственный способ, работающий на пустой системе.
2. **Получить признак от другого администратора**: он открывает «Управление пользователями» и нажимает иконку щита в столбце «Админ» напротив вашей учётной записи.

Что происходит после выдачи прав: при входе сразу открывается панель администратора, а не рабочая область; доступны все пять разделов; данные всех пользователей, проектов и ролей видны без ограничений; проекты, в которых вы не участник, открываются с правами руководителя проекта автоматически.

Проверки прав работают на двух уровнях: в интерфейсе обычному пользователю админка не показывается и попытка открыть её возвращает на главную страницу; на сервере каждый запрос к административным разделам проверяет признак суперпользователя, при его отсутствии сервер отвечает отказом 403.

Снять права с самого себя нельзя: сервер отклоняет такой запрос, а интерфейс не даёт его выполнить. Это защита от случайной потери единственного администратора.

Заблокированный пользователь теряет доступ ко всем разделам, включая административный: блокировка проверяется при каждом запросе, действующий токен входа не помогает.

## 2. Панель администратора

Панель открывается на адресе `/admin` и состоит из пяти плиток:

| Плитка | Раздел | Что внутри |
|---|---|---|
| Управление пользователями | `/admin/users` | Учётные записи, блокировка, права админа, право создавать проекты |
| Управление ролями | `/admin/roles` | Проектные роли и наборы прав |
| Управление проектами | `/admin/projects` | Все проекты, их участники и роли |
| Управление нейросетевыми моделями | `/admin/models` | Включение, выгрузка и прогрев моделей |
| Управление хранилищем | `/admin/storage` | Лимиты вложений, корзина, автоочистка |

Внизу стартового экрана расположен информационный блок о неограниченном доступе суперпользователя. Он носит предупреждающий характер: любое изменение здесь затрагивает всю платформу и все проекты, включая чужие. В шапке страницы показаны хлебные крошки — они позволяют вернуться к списку разделов.

Общие правила работы с панелью:

- изменения применяются сразу и переживают перезапуск, если не указано иное;
- настройки моделей и хранилища хранятся в базе данных, а не в файле настроек;
- состав данных на экране обновляется при каждом открытии раздела, поэтому изменения другого администратора видны без перезагрузки страницы.

## 3. Пользователи

Раздел «Управление пользователями» — список всех учётных записей. Кнопка добавления находится в правом верхнем углу.

### 3.1 Таблица и поиск

В таблице видны: аватар, полное имя, email, статус, признак администратора, признак «может создавать проекты» и действия. Поиск в поле над таблицей ищет одновременно по имени и по email; он выполняется на сервере, поэтому работает и на больших объёмах.

Ограничение: за один запрос сервер возвращает не больше 100 учётных записей, а постраничной навигации в интерфейсе нет. На системе, где пользователей больше сотни, искомого человека ищите поиском — без него список показан не целиком.

### 3.2 Создание пользователя

| Поле | Назначение |
|---|---|
| Логин / Email | Обязательное. Используется для входа |
| Полное имя | Отображается в интерфейсе и в списках |
| Пароль | Обязательное при создании, есть показ и скрытие символов |
| Админ | Признак суперпользователя |
| Создание проектов | Разрешение создавать проекты |

Создание пользователя с уже существующим email сервер отклоняет. При смене адреса у существующего пользователя такая проверка не выполняется — задавайте новый адрес внимательно.

### 3.3 Редактирование пользователя

Иконка карандаша в столбце «Действия» открывает то же окно. При редактировании поле пароля можно оставить пустым — тогда старый пароль сохранится. Признаки «Админ», «Создание проектов» и статус меняются и здесь, и отдельными кнопками в таблице; результат одинаковый.

### 3.4 Блокировка и разблокировка

Переключатель находится в столбце «Статус»: клик по бейджу «Активен» переводит пользователя в состояние «Заблокирован», клик по «Заблокирован» возвращает доступ.

Блокировка обратима и ничего не удаляет: доступ к системе закрывается при следующем же запросе (действующий токен не помогает), а проекты, задачи, история и права администратора сохраняются и вернутся вместе с доступом. Восстановление — тот же переключатель; для полного удаления используйте корзину в столбце «Действия».

### 3.5 Права администратора

Иконка щита в столбце «Админ» включает и выключает признак суперпользователя; для собственной учётной записи действие заблокировано.

Практическое замечание: у суперпользователя внутри любого проекта права руководителя проекта, даже если он в этом проекте не состоит. Это удобно для разбора инцидентов, но означает способность изменить содержимое чужого проекта. Договоритесь о правилах внутри команды до выдачи прав.

### 3.6 Право создавать проекты

Иконка галочки в столбце «Создание проектов» управляет правом создавать новые проекты. По умолчанию оно выключено у всех, кто зарегистрировался сам; включено только у учётной записи первого запуска и у тех, кому вы дали его явно. Снятие права не удаляет уже созданные проекты — оно лишь запрещает создавать новые.

### 3.7 Удаление пользователя

Иконка корзины в столбце «Действия» удаляет учётную запись после подтверждения. Удалять себя нельзя: действие недоступно, сервер его отклоняет.

| Что | Результат при удалении |
|---|---|
| Учётная запись и участие в проектах | Удаляются |
| Проекты, которыми пользователь владел | Остаются в системе без владельца, который мог бы ими управлять |
| Задачи, комментарии, история | Остаются на месте |

Поэтому удаление — не замена блокировке. Если данные пользователя могут понадобиться, блокируйте учётную запись; удаляйте только те, чьи данные больше не нужны.

## 4. Роли и права доступа

В системе два уровня прав: **администратор платформы** (раздел 1) и **проектные роли** (этот раздел). Проектная роль не даёт доступа к админке.

### 4.1 Системные и пользовательские роли

| Тип роли | Что это | Можно ли удалить |
|---|---|---|
| Системная | Пять базовых ролей: руководитель проекта, менеджер, разработчик, тестировщик, наблюдатель | Нет: кнопка удаления скрыта, сервер отклоняет запрос |
| Пользовательская | Любая роль, созданная вами в панели | Да |

В карточке роли видны название, описание, число назначенных прав и — у системных — метка «Системная роль».

Создание и правка роли: заполните название, описание и отметьте нужные права в сетке чекбоксов. Под сеткой показывается счётчик выбранных прав и подпись о том, что права применяются глобально во всех проектах, где используется роль. Отдельных прав на уровне отдельного проекта не существует.

### 4.3 Матрица прав по умолчанию

Права применяются из двух источников, и это важно понимать администратору:

1. если в базе данных есть запись роли с таким именем — применяется **набор прав из этой записи**, то есть ровно то, что вы отметили в панели;
2. если записи в базе нет — применяется **встроенная матрица** по названию роли.

| Роль | project | board | task | comment | pr |
|---|---|---|---|---|---|
| Руководитель проекта | Все 11 | Все 3 | Все 13 | Все 3 | Все 4 |
| Менеджер | 8: без удаления проекта и подключения репозитория | Все 3 | Все 13 | Все 3 | Все 4 |
| Разработчик | Просмотр, метки | Просмотр и перемещение | Создание, просмотр, правка, назначение, приоритет, срок, подзадачи, закрытие, Git, подтверждение моделей | Создание и правка своих | Просмотр, комментарий, одобрение, слияние |
| Тестировщик | Просмотр | Просмотр и перемещение | Создание, просмотр, назначение на себя, метки, подзадачи, закрытие, Git, подтверждение моделей | Создание и правка своих | Просмотр, комментарий, одобрение |
| Наблюдатель | Просмотр | Просмотр | Просмотр | — | Просмотр |

Практические следствия:

- **Правка роли через панель полностью заменяет матрицу**, а не дополняет её: сняли право — оно пропало, даже если есть в матрице.
- **Удаление роли из базы возвращает систему к матрице.** Если вы создали пользовательскую роль, надели её участникам и затем удалили роль, участники останутся в проекте, но права станут матричными — то есть, скорее всего, отсутствующими, потому что имя пользовательской роли в матрице не известно. Снимайте участников с удаляемой роли заранее.
- **Встроенную матрицу изменить из интерфейса нельзя**: у системных ролей есть записи в базе, и матрица к ним не применяется, пока запись существует. Чтобы изменить поведение системной роли, отредактируйте её через панель как обычную.

### 4.4 Ограничения, действующие поверх прав

Часть правил задана не правами, а кодом, и обойти их из панели нельзя:

| Правило | Смысл |
|---|---|
| Разработчик и тестировщик правят только задачи, назначенные на себя | Даже при выданном праве на правку чужих задач сервер отклонит изменение |
| Тестировщик не может назначать задачи другим участникам | Право в матрице есть, но сервер ограничивает |
| Разработчик может переназначить только задачу, над которой работает | Аналогичное ограничение |
| Менеджер не может назначить роль «Руководитель проекта» | Защита от появления второго руководителя в обход владельца |
| Менеджер не может удалить участника с ролью «Руководитель проекта» | То же ограничение на удаление |
| Удалить проект может только владелец или администратор | Право на удаление в ролях не выдаётся |
| Суперпользователь получает права руководителя проекта автоматически | Даже если участником проекта он не является |

## 5. Проекты (администрирование)

Раздел «Управление проектами» показывает все проекты системы, включая те, в которых администратор не состоит. Это основной инструмент разбора инцидентов и централизованного управления составом команд.

### 5.1 Список и поиск

В списке видны название проекта, его идентификатор, описание и владелец (имя и email). Поиск фильтрует список по названию и описанию прямо в браузере, без обращения к серверу, поэтому работает мгновенно. Если проектов нет, показывается пустое состояние «Проектов пока нет».

### 5.2 Участники проекта

Кнопка «Участники» открывает состав команды проекта. Из админки доступны четыре действия:

| Действие | Как выполнить | Эффект |
|---|---|---|
| Просмотр состава | Открыть «Участники» | Список: имя, email, роль |
| Добавление участника | «Добавить» → поиск по имени или email → выбор роли → «Добавить» | Участник появляется в проекте сразу |
| Смена роли участника | Выбрать роль напротив участника | Новая роль применяется немедленно |
| Удаление участника | Иконка удаления напротив участника | Запись об участии снимается |

Отличия от обычного окна участников, доступного руководителю проекта:

- **нет приглашения и подтверждения** — участник добавляется сразу, отдельного запроса на принятие не происходит;
- **нет проектных ограничений по ролям** — администратор может назначить роль «Руководитель проекта» и удалить участника с этой ролью, хотя в обычном окне такие действия менеджеру запрещены;
- **нет проверки на участие в другом проекте** — один человек может быть участником сколько угодно проектов;
- **удаление участника не трогает данные** — задачи, комментарии, коммиты и история остаются, исчезает только запись об участии.

Если выбранная роль по какой-то причине не найдена в базе, участник записывается с базовой ролью «Разработчик». После назначения стоит проверить в «Управлении пользователями», что человек активен: заблокированный участник не сможет работать в проекте.

### 5.3 Настройки проекта

Кнопка «Настройки» открывает обычное окно настроек проекта — то же, что видит руководитель проекта: вкладка подключения Git, фон проекта, удаление проекта. Разница только в проверке прав: администратору доступно то, что недоступно участнику, в том числе удаление проекта. Операция необратима.

### 5.4 Смена роли в обычном окне участников

В пользовательском окне участников проекта смена роли выпадающим списком сейчас не работает: интерфейс отправляет запрос, для которого на сервере нет обработчика. Работает только админский путь из этого раздела. Если пользователи жалуются, что роль «не сохраняется», ведите изменения здесь.

## 6. Нейросетевые модели

Раздел «Управление нейросетевыми моделями» — единственное место, где включаются, выгружаются и прогреваются модели анализа кода и оценки объёма работы.

### 6.1 Какие модели есть и что каждая делает

| Модель | Вид | Назначение | Зависимости |
|---|---|---|---|
| Кодировщик трассировки | Нейросеть | Переводит сообщения коммитов и тексты задач в векторы, по ним подбирает задачу для коммита. Самая тяжёлая часть: около гигабайта весов, в памяти держатся постоянно | — |
| Классификатор типов коммитов | Нейросеть | Определяет тип коммита по смыслу изменений: исправление, функциональность, рефакторинг, документация, тесты, прочее | Работает поверх кодировщика, отдельно не включается |
| Оценка объёма работы | Правила | Считает прогресс задачи по объёму изменений, подзадачам и файлам, названным в описании. Нейросеть не используется | — |

В верхней части страницы три метрики: суммарный объём артефактов на диске, сколько моделей загружено в память прямо сейчас и сколько включено.

### 6.2 Артефакты и где они лежат

| Артефакт | Имя по умолчанию | Размер | Что это |
|---|---|---|---|
| Веса кодировщика | `commit_tracer.pt` | ≈ 1061 МБ | Основные веса модели сопоставления |
| Веса классификатора | `type_classifier.pt` | ≈ 0,8 МБ | Только «голова» классификатора поверх замороженного кодировщика |
| Папка токенизатора | `paraphrase-multilingual-mpnet-base-v2` | ≈ 13,5 МБ | Пять файлов: конфигурация архитектуры, словарь и его описание |

Где брать файлы: они лежат в репозитории, в папке `code_model` рядом с кодом, то есть `backend/app/ai/code_model`. Клонирование даёт готовый комплект: веса обеих моделей, модуль правил прогресса и папку со словарём. Ничего скачивать и никуда класть руками не нужно.

Корень переопределяется переменной `CODE_MODEL_DIR` — она нужна только в контейнере, где артефакты подключают монтированием. Имена файлов весов заданы переменными `CODE_MODEL_TRACER_FILE` и `CODE_MODEL_CLASSIFIER_FILE`, имя папки словаря фиксировано.

Критически важно:

- **В файлах весов лежат только веса.** Архитектура модели и словарь берутся из папки токенизатора. Без неё модель **не запустится**: панель покажет метку «файл не найден», а в диагностике — причину `tokenizer_missing`.
- **Словарь и веса лежат в репозитории.** Клонирование даёт готовый комплект: веса обеих моделей, модуль правил прогресса и папку со словарём. Скачивать и раскладывать вручную ничего не нужно. Если словарь потерялся, восстановить его можно отдельно: `python backend/scripts/fetch_tokenizer.py`, проверка без скачивания — `python backend/scripts/fetch_tokenizer.py --check`.
- **Крупные веса хранятся через Git LFS.** Кодировщик весит около гигабайта, а у GitHub жёсткий предел 100 МБ на файл, поэтому обычным git он не загрузится. Если копировать репозиторий мимо LFS, клонирование пройдёт, но файлы останутся маленькими указателями и модель покажет причину `tracer_missing`. Перед клонированием выполните `git lfs install`; проверить состояние — `git lfs ls-files`.
- **Нужен `torch`, и его нет в списке зависимостей сервера.** Он ставится отдельной командой, указанной в самом файле зависимостей: сначала `torch` с индекса для CPU, затем `transformers` и `numpy`. Без него образ Docker соберётся и запустится, но работать с моделями не сможет: страница покажет, что артефакты на месте, а загрузка завершится ошибкой импорта. Полный `torch` тянет за собой сборку с видеоподдержкой объёмом около 2,5 ГБ — поэтому рекомендуется вариант для CPU. Для сборки образа предусмотрен отдельный аргумент сборки, который добавляет `torch` в образ; без него образ работает без моделей, и это осознанное решение.
- Модели занимают около 1,1 ГБ на диске и около 1,6 ГБ оперативной памяти при работе на CPU. Проверьте запас диска и памяти до включения.

### 6.3 Включение и выключение

Кнопка питания в карточке модели переключает её состояние. Решение пишется в базу данных, действует немедленно, перезапуск не требуется, между перезапусками сохраняется.

| Что важно понимать | Как это работает |
|---|---|
| Два источника состояния | До первого вашего решения действует значение из файла настроек; после — решение из базы |
| Метка «изменено» | Ваше решение расходится со значением из файла настроек. Это подсказка, а не ошибка |
| Кто и когда | Имя автора и время изменения сохраняются и показываются на карточке |
| Зависимости | Классификатор нельзя включить при выключенном кодировщике: сервер отклонит запрос и предложит сначала включить кодировщик |
| Выключение ≠ выгрузка | Выключение прекращает использование модели, но не освобождает память — для этого нужна выгрузка (раздел 6.4) |

Метки на карточке модели: «нейросеть» или «правила» — вид модели; «в памяти» — модель загружена в работающем процессе; «изменено» — решение администратора отличается от значения в файле настроек; «изменено: имя» — кто последним менял настройку; «файл не найден» — артефакт отсутствует на диске по указанному пути; «работает поверх модели «…»» — модель использует результаты другой; «не сработает, пока выключена «…»» — модель заблокирована выключенной зависимостью.

Путь к файлу и его размер в мегабайтах показываются прямо на карточке — это самый быстрый способ убедиться, что артефакт на месте.

### 6.4 Выгрузка из памяти

Кнопка «Выгрузить» освобождает память, не выключая модель. Кнопка доступна только для нейросетей, у которых артефакт действительно найден на диске.

| Правило | Что происходит |
|---|---|
| Кодировщик | Выгружается вместе с классификатором: без него классификатор считать нечем |
| Классификатор | Выгружается отдельно и весит меньше мегабайта — его можно убрать из памяти, не трогая кодировщик |
| Оценка объёма | Выгрузить нельзя: это набор правил, они не занимают памяти, сервер объяснит отказ |
| Повторная загрузка в том же процессе | Ненадёжна: освобождённый блок удерживается аллокатором |
| Что делать после выгрузки | Нажать «Загрузить» в шапке страницы или перезапустить сервер |

Выгрузка уместна, когда модели нужны редко, а память требуется другим задачам. Учтите, что после выгрузки первое обращение к модели будет медленным: веса читаются заново с диска.

### 6.5 Прогрев при старте

Загрузка весов занимает секунды, поэтому модель прогревается фоновой задачей при старте сервера и не блокирует запуск приложения. Модели грузятся лениво: выключенная модель не читает веса и вообще не подключает тяжёлые зависимости — сервер работает и без артефактов.

Условия фонового прогрева при старте должны выполняться одновременно:

1. модели анализа кода разрешены в файле настроек;
2. определение типов коммитов разрешено в файле настроек;
3. кодировщик включён с учётом решения из базы данных.

Следствие: если вы в файле настроек выключили определение типов коммитов, фоновый прогрев при старте не запустится, даже если в панели эти модели включены. Модель поднимется лениво — при первом обращении, то есть когда она уже нужна. Для предсказуемого поведения держите флаги файла настроек включёнными.

Ручной прогрев: кнопка «Загрузить» в шапке страницы перечитывает решения из базы и прогревает включённые модели. Если кодировщик выключен, сервер ответит, что прогрев пропущен, — это штатное поведение, а не ошибка.

### 6.6 Диагностические эндпоинты и их ограничение по доступу

Для проверки развёртывания есть два служебных запроса, которые делаются напрямую к серверу, минуя интерфейс:

| Запрос | Что делает |
|---|---|
| `GET /api/v1/ai/code-model/status` | Возвращает состояние: включена ли модель, на месте ли артефакты, загружена ли она в памяти, на каком устройстве работает |
| `POST /api/v1/ai/code-model/load` | Прогревает модель и возвращает то же состояние |

Что показывает состояние:

| Поле | Значение |
|---|---|
| Признак доступности | Готова ли модель к работе целиком |
| Причина недоступности | `disabled`, `tokenizer_missing`, `tracer_missing`, `classifier_missing`. Для классификатора дополнительно `encoder_disabled` |
| Готовность артефактов | Отдельно по папке токенизатора, весам кодировщика и весам классификатора |
| Каких файлов не хватает | Список отсутствующих файлов токенизатора |
| Загружена ли в память | Отдельно по кодировщику и классификатору |
| Устройство | `cpu` или `cuda` |
| Порог привязки | Текущее значение порога сопоставления коммита с задачей |
| Типы коммитов | Список поддерживаемых типов |

> **Ограничение по доступу.** Эти два запроса, а также запросы ручной трассировки
> и определения типа коммита, **не требуют авторизации**: они доступны любому,
> кто дотянулся до адреса сервера, включая анонимного посетителя. В
> пользовательском интерфейсе они не вызываются — ими пользуются вручную.
>
> Что это даёт нарушителю: сведения о том, какие файлы модели на месте, занята
> ли память и какие пороги настроены. Данные пользователей они не раскрывают.
>
> Рекомендация: **закройте эти пути на уровне обратного прокси** (правило
> запрета по маршруту) либо ограничьте внешний доступ к серверу. Свой
> авторизованный аналог есть в панели: «Управление нейросетевыми моделями».

## 7. Хранилище и лимиты

Раздел «Управление хранилищем» регулирует, сколько места могут занимать вложения, как долго они лежат после удаления и что происходит при превышении квоты. Все настройки хранятся в базе данных и применяются без перезапуска: они перечитываются при каждой загрузке файла и на каждом проходе очистки корзины.

### 7.1 Что занимает место

| Показатель | Что считает |
|---|---|
| Всего на диске | Сумма трёх следующих строк |
| Активные | Вложения, прикреплённые к задачам |
| Корзина | Вложения, помеченные удалёнными, но ещё лежащие на диске |
| Неприкреплённые | Файлы, загруженные, но не привязанные ни к одному комментарию |

Важное уточнение: в сводку входят **только вложения задач**. Аватары пользователей и фоны проектов занимают место в том же каталоге хранения, но в этих цифрах не отражаются. Если каталог растёт быстрее, чем показывают цифры, ищите расхождение в этих файлах.

### 7.2 Лимиты вложений и лимиты проектов

Блок «Лимиты вложений»:

| Настройка | Допустимый диапазон | По умолчанию | Что делает |
|---|---|---|---|
| Максимальный размер файла | 1…1024 МБ | 25 МБ | Файлы крупнее отклоняются при загрузке |
| Лимит нового проекта | 1…102400 МБ | 500 МБ | Действует на проекты без собственного лимита |
| Разрешённые расширения | список | `.png,.jpg,.jpeg,.gif,.pdf,.doc,.docx,.txt,.zip,.log` | Файлы других типов отклоняются при загрузке |

Список расширений вводится через запятую: точка в начале добавляется автоматически, повторы убираются, порядок сортируется. Пустой список сохранить нельзя — такая настройка сделала бы загрузку невозможной. Кнопка «Сохранить» активна, только если есть несохранённые изменения; значения вне диапазона сервер отклоняет и показывает допустимые границы.

Блок «Проекты» — индивидуальные квоты:

| Действие | Что происходит |
|---|---|
| «Задать» со значением в МБ | У проекта появляется собственный лимит |
| «Вернуть общий» | Проект возвращается к общему лимиту из настроек |
| Полоса заполнения | Зелёная до 60 %, янтарная от 60 до 90 %, красная от 90 % |
| Метка «общий лимит» | Показывается у проектов без собственного лимита |

Проекты выводятся по убыванию расхода: самые «тяжёлые» сверху.

### 7.3 Корзина и автоочистка

| Настройка или действие | Допустимый диапазон | По умолчанию | Что делает |
|---|---|---|---|
| Срок хранения | 0…365 дней | 7 дней | Через сколько дней удаление становится необратимым |
| Проверять корзину (интервал) | 1…168 часов | 6 часов | Как часто запускается автоочистка. Поле блокируется, если автоочистка выключена |
| Очищать автоматически | — | Включено | Фоновая задача стартует вместе с сервером |
| Очистить просроченное | — | — | Удаляет только то, что перевалило за срок хранения |
| Очистить корзину целиком | — | — | Удаляет всё содержимое корзины независимо от срока, после подтверждения |

Под полем срока показывается счётчик: сколько записей уже старше срока хранения и исчезнет при ближайшей автоочистке. Кнопка «Очистить просроченное» активна, только когда такие записи есть.

**Главное, что должен понимать администратор:** удаление вложения не удаляет файл с диска. Вложение лишь помечается удалённым и уезжает в корзину; сам файл продолжает занимать место, пока корзина не будет очищена. Место в квоте проекта освобождается тоже при очистке, а не в момент удаления.

Загрузка сначала создаёт запись со статусом «неприкреплён», а привязка к комментарию происходит позже. Если привязки не случилось, запись удаляется через 24 часа — но только в ходе фоновой очистки.

### 7.4 Что происходит при превышении квоты

При загрузке файла проверки идут строго в этом порядке:

| Порядок | Проверка | Что видит пользователь при отказе |
|---|---|---|
| 1 | Размер файла | Сообщение о превышении максимального размера с указанием лимита |
| 2 | Расширение | Сообщение о недопустимом типе файла со списком разрешённых |
| 3 | Квота проекта | Сообщение о достижении лимита хранилища проекта |

Счётчик расхода проекта увеличивается только после успешной загрузки, поэтому неудачные попытки квоту не расходуют.

Особенность расчёта: лимит проекта — индивидуальный, если он задан, иначе берётся общий лимит из настроек. Проекты, созданные до изменения общего лимита, автоматически под него попадают, но их индивидуальные лимиты остаются в силе. Если пользователи жалуются на неожиданные отказы, проверьте здесь текущие значения лимитов и расход конкретного проекта по полосе заполнения.

## 8. Журналы и аудит

В системе четыре источника истории. Ни один из них не является полным журналом действий администраторов — об этом честно сказано в конце раздела.

### 8.1 Журнал активности задач

Каждое изменение по задаче фиксируется отдельной записью. Записываются десять типов событий:

| Тип события | Когда появляется |
|---|---|
| Создание задачи | Карточка создана |
| Смена статуса | Задача перемещена между колонками |
| Смена исполнителя | Назначен или снят исполнитель |
| Смена приоритета | Изменён приоритет |
| Добавлен комментарий | Оставлен комментарий |
| Добавлена подзадача | В чек-лист добавлен пункт |
| Смена статуса подзадачи | Отмечен пункт чек-листа |
| Удалена подзадача | Пункт чек-листа удалён |
| Добавлено вложение | Файл загружен в задачу |
| Удалено вложение | Файл помечен удалённым |

Где смотреть: вкладка «История» в карточке задачи и вкладка «История» на доске проекта. Записи содержат автора, время и описание изменения.

### 8.2 Журнал Git-событий

События, пришедшие от провайдера через вебхук, попадают в журнал Git-событий вместе с отметкой, прошла ли подпись события. Журнал виден в ленте активности проекта и в истории задачи. Для администратора это основной источник разбора: «приходили ли события вообще» и «принимались ли они».

### 8.3 События без привязки

События, которые не удалось соотнести с задачей, попадают в отдельный список: настройки проекта → вкладка «Непривязанные события». Такое событие можно вручную привязать к задаче прямо оттуда. Большое число непривязанных событий означает, что правила разбора ссылок не срабатывают — обычно из-за другого формата сообщений коммитов в этом репозитории.

### 8.4 Кто и когда менял настройки

| Что | Где хранится | Где видно |
|---|---|---|
| Настройки моделей | Имя автора и время изменения | Метка «изменено: имя» на странице моделей |
| Настройки хранилища | Автор изменения сохраняется в базе | **В интерфейсе не отображается** |

Если вам нужно знать, кто изменил лимиты, смотрите записи в базе данных напрямую.

### 8.5 Чего нет: журнала действий администраторов

**Отдельного журнала действий администраторов в системе нет.** Это отсутствующая функциональность, а не ограничение настройки. Не журналируются: выдача и снятие прав администратора; блокировка и удаление учётных записей; изменение ролей и прав ролей; изменение лимитов хранилища и настроек корзины; изменение настроек моделей (сохраняются только автор и время, без истории «с какого значения на какое»); добавление, смена роли и удаление участников проекта через админку.

Что делать вместо этого:

- включайте серверные логи и сохраняйте их: там фиксируются ошибки фоновых задач и обслуживания хранилища;
- договоритесь о правиле: настройки меняет один ответственный, а значимые правки фиксируются во внутреннем журнале организации;
- при инциденте ориентируйтесь на журналы из разделов 8.1–8.3 и на метку автора у настроек моделей.

## 9. Развёртывание

Этот раздел описывает боевое развёртывание. Всё, что здесь перечислено,
нужно для работающей установки, доступной пользователям.

### 9.0 Боевой запуск: краткий порядок

| Шаг | Что сделать | Чем проверить |
|---|---|---|
| 1 | Поднять базу данных и Redis | `docker compose ps` — оба сервиса в состоянии «здоровы» |
| 2 | Скопировать `backend/.env.example` в `backend/.env` и задать `SECRET_KEY` | Файл существует, ключ не равен значению по умолчанию |
| 3 | Собрать образ сервера | `docker compose build backend` |
| 4 | Применить миграции | `docker compose run --rm backend alembic upgrade head` |
| 5 | Запустить сервер | `docker compose up -d backend`, затем `docker compose logs -f backend` |
| 6 | Сменить пароль первого администратора (раздел 9.3) | Вход под новым паролем проходит |
| 7 | Задать `PUBLIC_BASE_URL` на внешний адрес | Проверка подключения репозитория в настройках проекта проходит |
| 8 | Раздать интерфейс и направить на него прокси | Интерфейс открывается по внешнему адресу |

Порядок не произвольный. Миграции идут **до** первого входа: иначе
сервер поднимется на пустой схеме. Внешний адрес задаётся **до**
подключения репозиториев: из него строятся адреса вебхуков, и сменить
адрес после регистрации вебхуков значит перерегистрировать их.

### 9.1 Чем рабочий режим отличается от режима разработки

Разница не косметическая: в режиме разработки часть того, что сломается
в бою, просто не выполняется.

| Что | Разработка | Рабочий режим |
|---|---|---|
| Запуск сервера | `uvicorn app.main:app --reload` | `uvicorn app.main:app` без `--reload`; сервер не перезапускается сам при правке файлов и не читает исходники в горячем режиме |
| Интерфейс | `npm run dev`, порт 3000, прокси на сервер из разработки | `npm run build` и раздача готовых файлов веб-сервером |
| Порт сервера | 8000, открыт наружу для отладки | Закрыт: наружу смотрит только прокси, который отдаёт интерфейс |
| Отладочный режим | Включён | Выключен |
| Артефакты моделей | В папке проекта | Подключены монтированием или скопированы в образ |
| Кросс-доменные запросы | Разрешены отовсюду | Ограничены прокси (раздел 9.2.3) |

### 9.1.1 Раздача интерфейса

Сервер отдаёт программный интерфейс приложения, а не статику интерфейса.
Интерфейс собирается отдельно и раздаётся веб-сервером перед сервером
приложения.

Сборка:

```bash
cd frontend
npm ci
npm run build
```

На выходе получается папка `frontend/dist`. Её нужно отдать веб-сервером,
который:

1. отдаёт `frontend/dist` как корень сайта;
2. перенаправляет любые неизвестные адреса на `index.html` — иначе
   переход по прямой ссылке внутри приложения даст ошибку;
3. перенаправляет запросы на `/api/`, `/uploads/` и `/manuals/` на сервер
   приложения;
4. выпускает сертификат, если доступ по HTTPS.

Блок переадресации выглядит так:

```
location /api/    { proxy_pass http://127.0.0.1:8000; }
location /uploads/ { proxy_pass http://127.0.0.1:8000; }
location /manuals/ { proxy_pass http://127.0.0.1:8000; }
location /        { try_files $uri $uri/ /index.html; }
```

> Закрыть снаружи маршруты `/api/v1/ai/code-model/` — они не требуют
> авторизации и показывают состояние моделей (раздел 6.6).

### 9.1.2 Артефакты моделей в рабочем режиме

Образ сервера собирается **без** весов моделей: кодировщик весит около
гигабайта, и класть его в образ на каждый запуск незачем. Артефакты
подключаются отдельно и переживают пересборку образа.

Положите файлы в папку вне репозитория, раскладка повторяет структуру
моделей в проекте:

```
models/code_model/commit_tracer.pt
models/code_model/type_classifier.pt
models/code_model/paraphrase-multilingual-mpnet-base-v2/
```

Затем в `docker-compose.yml` раскомментируйте подключение и задайте
корень:

```yaml
    environment:
      CODE_MODEL_DIR: /app/models
    volumes:
      - ./models:/app/models:ro
```

Подключение только на чтение: сервер артефакты не изменяет, а случайная
запись в подключённую папку не должна портить файлы, заменённые вручную.

Если сервер запускается без Docker, тот же путь задаётся в `backend/.env`.

### 9.1.3 Проверка после развёртывания

| Что проверить | Как |
|---|---|
| Сервер отвечает | `docker compose ps` — сервер «здоров»; либо `curl` на `http://127.0.0.1:8000/` |
| Схема базы на месте | `docker compose exec backend alembic current` |
| Модели загружаются | `curl` на `http://127.0.0.1:8000/api/v1/ai/code-model/status` |
| Артефакты на месте | Там же: раздел «Готовность артефактов» по кодировщику и классификатору |
| Интерфейс открыт | Открыть внешний адрес в браузере |
| Проверка подключения репозитория | Настройки проекта → вкладка Git → «Проверка подключения» |

Пока модуль моделей не загружен, сервер работает: анализ кода просто
не выполняется. Это осознанное поведение, а не поломка — см. раздел 6.1.

### 9.1.4 Требования

Два варианта развёртывания: Docker Compose — поднимаются три сервиса (база данных PostgreSQL 16, Redis 7 и сервер приложения на порту 8000); ручная установка — Python 3.10 или новее, Node.js 18 или новее, PostgreSQL и Redis.

Ресурсы: около 1,1 ГБ диска на артефакты моделей, если они используются, и около 1,6 ГБ оперативной памяти сверх обычного потребления при загруженном кодировщике. Видеокарта не требуется: модели работают на CPU, настройка по умолчанию — автоопределение, при нехватке ресурсов можно принудительно указать CPU. Git нужен и серверу, и пользователям.

### 9.2 Переменные окружения

Файл переменных — `.env` в рабочем каталоге процесса сервера. Имена регистрозависимы: `SECRET_KEY` и `secret_key` — разные вещи, опечатка в регистре молча оставит значение по умолчанию. Файл `docker-compose.yml` передаёт внутрь контейнера только две переменные — подключение к базе и к Redis; все остальные сервер читает из файла, который должен оказаться внутри контейнера.

#### 9.2.3 Безопасность

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `SECRET_KEY` | `SUPER_SECRET_KEY_CHANGE_ME` | Ключ подписи входных токенов и базовый ключ шифрования токенов Git |
| `ALGORITHM` | `HS256` | Алгоритм подписи токенов |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | `604800` (7 суток) | Срок жизни входного токена |
| `TOKEN_ENCRYPTION_KEY` | пусто | Ключ шифрования токенов Git-провайдеров при хранении |

> **Кросс-доменные запросы разрешены отовсюду.** Сервер принимает обращения
> с любого адреса, любыми методами и заголовками. Пока клиент и сервер стоят
> на одном адресе или рядом, это безвредно. Как только сервер выставлен в
> интернет, ограничьте список разрешённых источников на обратном прокси:
> открытый список означает, что страницу вашего приложения можно открыть
> с чужого домена и оттуда ходить в API от имени вошедшего пользователя.

> **`SECRET_KEY` обязателен к замене.** Значение по умолчанию общеизвестно: любой
> может подделать входной токен и войти с правами администратора. Задайте
> случайную строку достаточной длины.
>
> **`TOKEN_ENCRYPTION_KEY` и `SECRET_KEY` связаны.** Если ключ шифрования не
> задан явно, он выводится из `SECRET_KEY`. Поэтому:
>
> - если токены Git-провайдеров **ещё не сохранялись** — можно задать
>   `SECRET_KEY` и не задавать `TOKEN_ENCRYPTION_KEY`;
> - если токены **уже зашифрованы и сохранены** — **менять `SECRET_KEY` и
>   `TOKEN_ENCRYPTION_KEY` нельзя**. Сохранённые токены перестанут
>   расшифровываться, все подключённые Git-аккаунты перестанут работать, и
>   пользователям придётся подключать их заново.
>
> Практический вывод: задайте оба ключа явно и храните их в надёжном месте
> **до** первого подключения репозиториев.

#### 9.2.7 Модели анализа кода

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `CODE_MODEL_ENABLED` | `True` | Общий выключатель моделей анализа кода; значение по умолчанию для кодировщика |
| `CODE_MODEL_DIR` | пусто — искать рядом с кодом | Корень, в котором лежат папки моделей. Задавайте, только если артефакты не там |
| `CODE_MODEL_TRACER_FILE` | `commit_tracer.pt` | Имя файла весов кодировщика |
| `CODE_MODEL_CLASSIFIER_FILE` | `type_classifier.pt` | Имя файла весов классификатора |
| `CODE_MODEL_DEVICE` | `auto` | Устройство вычислений: `auto`, `cpu` или `cuda` |
| `CODE_MODEL_TRACE_THRESHOLD` | `0.30` | Порог привязки коммита к задаче. Ниже порога решение остаётся за человеком |
| `CODE_MODEL_TRACE_LIMIT` | `20` | Сколько задач проекта рассматривать при подборе |
| `CODE_MODEL_TRACE_BUDGET_SECONDS` | `5.0` | Бюджет времени на один коммит при массовом прогоне |
| `GIT_TRACE_ON_SYNC` | `False` | Трассировка по смыслу во время фоновой сверки |
| `GIT_TRACE_SYNC_LIMIT` | `10` | Сколько коммитов трассировать за один проход |
| `GIT_TRACE_FETCH_PATCHES` | `False` | Догружать ли тексты изменений прямо во время трассировки |
| `CODE_MODEL_CLASSIFY` | `True` | Определять тип коммита при привязке к задаче |

Значения этих переменных — только значения **по умолчанию**. После того как вы приняли решение на странице моделей, решает база данных, а не файл (раздел 6.3); метка «изменено» показывает, где решения расходятся.

Артефакты обеих моделей лежат в одной папке `app/ai/code_model`:

```
app/ai/code_model/commit_tracer.pt                      веса трассировки
app/ai/code_model/type_classifier.pt                    веса типов
app/ai/code_model/progress_estimator.py                 модуль правил
app/ai/code_model/paraphrase-multilingual-mpnet-base-v2/  конфиг и словарь
```

`CODE_MODEL_DIR` задаёт корень, внутри которого ищется папка `code_model`. Пустое значение означает «искать рядом с кодом»: путь не зависит от того, из какой папки запущен сервер. В контейнере задайте его явно, если артефакты подключены монтированием, — например `/app/models`.

#### 9.2.8 Тексты изменений

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `GIT_FETCH_PATCHES` | `False` | Запрашивать ли тексты изменений у провайдера |
| `GIT_MAX_PATCH_CHARS` | `4000` | Максимум символов текста изменений на файл |
| `GIT_PATCH_BACKFILL_LIMIT` | `50` | Сколько коммитов дозаполнять за один проход |
| `GIT_PATCH_BACKFILL_DELAY` | `0.3` | Пауза между запросами, чтобы не упереться в лимиты провайдера |

Тексты изменений выключены по умолчанию намеренно: это отдельный запрос к провайдеру на каждый коммит, и включение на большом проекте превращает сверку в сотни запросов. Модели заметно точнее, когда тексты изменений заполнены, поэтому на проектах, где важна точность трассировки, дозагрузку стоит включить и наполнить их заранее.

#### 9.2.9 Руководства

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `SERVE_DOCS` | `false` | Включает отдачу руководств по адресу `/manuals/<имя файла>` |
| `DOCS_DIR` | подбирается автоматически | Папка с текстами руководств |

Тексты лежат в папке `docs/` рядом с папкой `backend` — по два руководства, на русском и на английском:

```
docs/user-guide.md          docs/admin-guide.md
docs/user-guide.en.md       docs/admin-guide.en.md
```

Это единственные экземпляры файлов: их же открывают Git и страница справки внутри приложения, поэтому две копии текста разойтись не могут.

Язык подставляется по языку интерфейса. Если английское руководство положить рядом с русским, страница справки откроет нужное сама; если его нет — страница покажет ошибку загрузки.

Страница справки открывается из шапки **в новой вкладке**: чтение руководства не должно уводить с доски, на которой человек работал.

`DOCS_DIR` задавать обычно не нужно. Приложение само ищет папку рядом с собой, затем в корне репозитория. Значение требуется в контейнере, где структура папок другая: там тексты копируются в `/app/docs`, и переменная уже проставлена в образе.

Отдача руководств по умолчанию выключена намеренно: это руководство содержит секреты и перечень переменных окружения. Включайте её только внутри контура, где доступ к таким файлам допустим, и выключайте обратно.

Адрес `/docs` при этом занят встроенной документацией API и к руководствам отношения не имеет.

> **Важно: приложение не запустится при любой неизвестной переменной окружения.**
> Настройки загружаются с запретом лишних полей, поэтому неизвестная переменная в `.env` или в окружении контейнера обрывает старт с ошибкой проверки, а не игнорируется. Если сервер не стартует и в тексте ошибки упоминаются «extra inputs», ищите опечатку или устаревшую переменную в `.env` и в `docker-compose.yml`. Это касается и переменных, которые когда-то читались вручную: добавлять новые нужно в настройки приложения, иначе они не заработают.

### 9.3 Первый запуск и первый суперпользователь

При первом старте сервера, если в базе нет пользователя с идентификатором 1, автоматически создаётся учётная запись:

| Поле | Значение |
|---|---|
| Email | `admin@example.com` |
| Пароль | `admin` |
| Полное имя | `Default Admin` |
| Права администратора | Да |
| Право создавать проекты | Да |

В лог запуска при этом выводится сообщение о создании пользователя по умолчанию.

> **Обязательно смените пароль сразу после первого входа.**
>
> Учётные данные `admin@example.com` / `admin` опубликованы в документации
> проекта и известны любому, кто получил доступ к вашему серверу. До смены
> пароля любой посетитель может войти с полными правами администратора, выдать
> себе и другим права, отключить модели, сменить лимиты хранилища и удалить чужие
> данные.
>
> Порядок действий: войти под этой учётной записью → «Управление пользователями»
> → карандаш напротив себя → задать новый пароль → сохранить. Поле пароля при
> редактировании можно оставить пустым, если менять его не нужно.

Чего делать **нельзя**: задать эти данные через файл настроек невозможно. Переменных для логина и пароля первого администратора в приложении нет, а добавлять их нужно в настройки — новая переменная, прочитанная напрямую, не заработает (раздел 9.2.9). Логин и пароль первого администратора жёстко заданы в программном коде.

Дополнительно: проверка выполняется по идентификатору, а не по email. Если учётная запись с идентификатором 1 была удалена, при следующем старте сервера она будет создана заново с теми же данными. Это повод ещё раз проверить пароль.

### 9.4 Миграции базы данных

Схема базы применяется миграциями один раз при развёртывании. Сервер при старте миграции **не** выполняет намеренно: второй экземпляр приложения при перезапуске не должен менять схему чужой базы.

Порядок действий: (1) поднять базу данных и Redis; (2) собрать образ сервера — при необходимости с аргументом установки `torch`; (3) запустить контейнер сервера; (4) выполнить `docker compose exec backend alembic upgrade head`; (5) убедиться, что сервер отвечает, и войти первым администратором.

При ручной установке шаг 4 выполняется из каталога сервера командой `alembic upgrade head`, а запуск — командой `uvicorn app.main:app --reload` для разработки. Резервную копию базы делайте **до** обновления: миграции необратимы.

Артефакты моделей в образ не попадают: контекст сборки — корень репозитория, и копирование гигабайтного веса раздуло бы образ на гигабайт. Подключите их монтированием — раздел 9.1.2.

### 9.5 Токены провайдеров и OAuth

| Способ | Когда использовать | Что требуется |
|---|---|---|
| OAuth-приложение | Предпочтительный: пользователь один раз нажимает кнопку | Зарегистрировать приложение у провайдера и заполнить переменные из раздела 9.2.5 |
| Персональный токен | Пока OAuth не настроен | Пользователь сам выпускает токен у провайдера |

Порядок настройки OAuth:

1. Зарегистрируйте приложение у провайдера и получите идентификатор и секрет.
2. Заполните соответствующие переменные из раздела 9.2.5 и перезапустите сервер.
3. В качестве адреса возврата укажите адрес **сервера**: `{PUBLIC_BASE_URL}/api/v1/auth/oauth/{провайдер}/callback`.
4. Проверьте `OAUTH_FRONTEND_REDIRECT` — это адрес **интерфейса**, и по умолчанию он указывает на режим разработки.

Вебхуки на стороне провайдера должны принимать события `push` и `pull_request`. Адрес вебхуков выдаёт система в настройках проекта на вкладке Git; при включённой `GIT_WEBHOOK_AUTO_REGISTER` система пытается зарегистрировать вебхук сама через программный интерфейс провайдера — для этого у провайдера должны быть выданы права на управление вебхуками.

## 10. Обслуживание

### 10.1 Фоновая сверка Git

Сервер сам периодически обходит все подключённые репозитории и догружает коммиты, ветки и запросы на слияние. Эта задача выполняется **внутри процесса сервера**: отдельный работник очереди задач для неё не нужен, и расписание очереди в проекте не настроено.

| Параметр | Значение | Как изменить |
|---|---|---|
| Включена ли | Да | `GIT_SYNC_ENABLED` в файле настроек |
| Интервал | 5 минут | `GIT_SYNC_INTERVAL_SECONDS` в файле настроек, перезапуск сервера |
| Глубина первой сверки | 90 дней | `GIT_SYNC_SINCE_DAYS` |
| Глубина докачки за проход | 5 страниц по 100 записей | `GIT_SYNC_MAX_PAGES`, `GIT_SYNC_PAGE_SIZE` |

Признаки того, что сверка работает: в настройках проекта на вкладке Git видно время последней сверки и её статус; в истории проекта появляются новые коммиты без действий пользователей.

### 10.2 Фоновая дозагрузка правок и типов

Отдельная фоновая обработка запускается при ручной синхронизации репозитория (кнопка «Синхронизировать» в настройках проекта → Git) и идёт в три шага:

| Шаг | Что делает | Когда выполняется |
|---|---|---|
| 1 | Дозагружает тексты изменений для коммитов, у которых их нет | Если `GIT_FETCH_PATCHES` включён |
| 2 | Подбирает задачи для непривязанных коммитов по смыслу | Если `GIT_TRACE_ON_SYNC` включён |
| 3 | Досчитывает типы коммитов, для которых тип не был определён в момент привязки | Если модели анализа кода разрешены |

Процесс ограничен по времени: запрос ждёт конца обработки, но не дольше 90 секунд. Если модель считает дольше, пользователю показывают состояние «идёт разбор», а результат становится виден позже — при повторном открытии настроек. Это ожидаемое поведение, а не зависание.

Шаг 3 стоит держать в голове при разборе «почему у коммита нет типа»: тип досчитывается только для уже привязанных коммитов и только после того, как модель была доступна.

### 10.3 Автоочистка корзины

Фоновая задача очистки запускается при старте сервера, только если автоочистка включена в панели. Интервал берётся из настройки «Проверять корзину» и перечитывается на каждом проходе — изменение интервала не требует перезапуска. За один проход задача:

1. удаляет неприкреплённые файлы старше 24 часов;
2. удаляет из корзины всё, что старше срока хранения;
3. пересчитывает расход места по затронутым проектам.

Если автоочистку выключили, первый шаг тоже перестаёт выполняться: неприкреплённые файлы будут копиться и удерживать место в квотах проектов. Если вам нужен контроль над удалениями, но чистить такие записи необходимо, очищайте корзину вручную кнопкой «Очистить корзину целиком».

### 10.4 Если модель не грузится

| Шаг | Проверка | Что делать при проблеме |
|---|---|---|
| 1 | Откройте «Управление нейросетевыми моделями» | Посмотрите метку «файл не найден» и путь к файлу |
| 2 | Проверьте папку токенизатора | Она должна лежать рядом с весами и содержать пять файлов; без неё модель не запустится |
| 3 | Проверьте установку `torch` | Он ставится отдельно; в образе включается аргументом сборки |
| 4 | Посмотрите состояние через диагностический запрос | Причина недоступности расшифровывает проблему: выключено, нет папки токенизатора, нет весов кодировщика или классификатора |
| 5 | Проверьте запас памяти | Кодировщик требует около 1,6 ГБ; при нехватке памяти загрузка обрывается |
| 6 | Проверьте настройку устройства | При автоматическом выборе сервер может взять видеокарту; при нехватке ресурсов укажите `cpu` |
| 7 | Нажмите «Загрузить» на странице моделей | Прогрев включённых моделей заново |
| 8 | Перезапустите сервер | Помогает после выгрузки: повторная загрузка в том же процессе ненадёжна |

### 10.5 Логи

Сервер пишет логи в стандартный вывод, то есть в журнал контейнера или службы.

Что попадает в логи: создание пользователя по умолчанию при первом старте; готовность модели анализа кода и время её загрузки, а также неудачный прогрев с причиной; запуск и остановка циклов фоновой сверки и очистки; результаты проходов очистки корзины и удаления неприкреплённых файлов; необработанные ошибки фоновых циклов; ошибки доступа к настройкам моделей и хранилища при недоступности базы; ошибки фоновой обработки репозитория с указанием шага.

При недоступности базы настроек сервер не падает: он пишет предупреждение и продолжает работать на значениях по умолчанию. Та же логика и у настроек хранилища. Это удобно для устойчивости, но означает, что ваши настройки могут молча не применяться — при сомнениях сверяйтесь с панелью и с журналом.

## 11. Диагностика

### 11.1 Модели

| Симптом | Вероятная причина | Что проверить |
|---|---|---|
| Метка «файл не найден» | Артефакт отсутствует по указанному пути | Путь на карточке модели; наличие файла; правильно ли задан каталог артефактов в файле настроек |
| Причина `tokenizer_missing` | Нет папки токенизатора или части её файлов | Наличие пяти файлов токенизатора рядом с весами |
| Причина `tracer_missing` | Нет файла весов кодировщика | Наличие файла и его размер (около 1 ГБ) |
| Причина `classifier_missing` | Нет файла весов классификатора | Наличие файла; без него модель целиком считается недоступной, даже если кодировщик на месте |
| Причина `disabled` | Кодировщик выключен | Состояние кнопки питания и метка «изменено» на карточке |
| Модель включена, но не «в памяти» | Не выполнен прогрев либо модель выгружена | Кнопка «Загрузить»; при отказе — запись об ошибке в логах |
| Ошибка загрузки при наличии файлов | Не установлен `torch` | Установлен ли `torch`; для контейнера — пересборка с аргументом установки |
| Модель падает при работе на видеокарте | Недостаточно видеопамяти | Задать устройство `cpu` в файле настроек и перезапустить |
| Привязка не работает, хотя модели включены | Тексты изменений не загружены | Включить дозагрузку текстов изменений; состояние фоновой обработки репозитория |
| После «Выгрузить» модель не поднимается | Повторная загрузка в том же процессе ненадёжна | Нажать «Загрузить» или перезапустить сервер |
| После старта модель не прогрета | Не выполнено условие фонового прогрева | Флаги моделей и определения типов в файле настроек, состояние кодировщика в панели (раздел 6.5) |

### 11.2 Git-интеграция

| Симптом | Вероятная причина | Что проверить |
|---|---|---|
| Коммиты не появляются | Не настроен вебхук | Настройки проекта → Git → проверка подключения: отмечены ли все четыре шага |
| Вебхук настроен, события не приходят | Адрес вебхуков недоступен извне | Публичный адрес сервера в файле настроек; открыт ли адрес вебхука из интернета |
| События приходят, но подпись не проходит | Расхождение секретов | Перерегистрируйте вебхук в настройках проекта и внесите новый секрет у провайдера |
| Коммиты не привязываются к задачам | Формат сообщений не совпадает с ожидаемым | Настройки проекта → непривязанные события; велико ли их число |
| Коммиты привязаны не к той задаче | Слишком низкий порог сопоставления | Порог привязки в файле настроек: низкое значение даёт лишние привязки |
| Модель предлагает связь, человек не согласен | Это ожидаемо: ниже порога решение остаётся за человеком | Порог привязки и метки уверенности в истории задачи |
| Тип коммита не определён | Модель не была доступна в момент привязки | Запустить «Синхронизировать» — типы досчитываются для уже привязанных коммитов |
| «Идёт разбор» не исчезает | Фоновая обработка идёт дольше 90 секунд | Дождаться и обновить настройки: состояние обработки и её ошибка показываются там же |
| Репозиторий подключён, но данных нет | Фоновая сверка ещё не проходила | Подождать до 5 минут или нажать «Синхронизировать» |
| Синхронизация завершилась ошибкой | Токен истёк либо недостаточно прав | Текст ошибки последней синхронизации; состояние подключения аккаунта в профиле |

### 11.3 Хранилище

| Симптом | Вероятная причина | Что проверить |
|---|---|---|
| Загрузка отклоняется с ошибкой размера | Файл крупнее максимального размера | «Управление хранилищем» → «Максимальный размер файла» |
| Загрузка отклоняется с ошибкой типа | Расширения нет в списке разрешённых | «Разрешённые расширения»; точка добавляется автоматически |
| Загрузка отклоняется с ошибкой квоты | Проект исчерпал лимит | Полоса заполнения по проекту; при необходимости поднимите индивидуальный лимит |
| Место на диске не освобождается | Удалённые файлы лежат в корзине | «Корзина» и «Очистить просроченное»; срок хранения по умолчанию 7 дней |
| Место освобождается медленнее ожидаемого | Автоочистка выключена или выставлен длинный интервал | Чекбокс «Очищать автоматически» и поле «Проверять корзину» |
| Квота расходится с фактическим расходом | Счётчик пересчитывается при очистке | Выполните очистку корзины — расход пересчитается по затронутым проектам |
| Панель показывает не заданные вами значения | База настроек была недоступна, действуют значения по умолчанию | Запись о недоступности настроек хранилища в логах сервера |
| Загруженные «в никуда» файлы занимают место | Неприкреплённые записи старше 24 часов удаляются в фоне | Состояние «Неприкреплённые» в сводке; работает ли автоочистка |

### 11.4 Доступ и учётные записи

| Симптом | Вероятная причина | Что проверить |
|---|---|---|
| Админка недоступна, возврат на главную | У пользователя нет прав администратора | Столбец «Админ» в «Управлении пользователями» |
| Запрос к административному разделу отклонён с 403 | Нет прав на сервере | Сервер проверяет права независимо от интерфейса |
| Нельзя снять права с себя или удалить себя | Защита от потери единственного администратора | Ожидаемое поведение; второго администратора назначайте заранее |
| У пользователя пропал доступ | Учётная запись заблокирована | Столбец «Статус»; блокировку снимает тот же переключатель |
| Правка роли не дала эффекта | В базе нет записи этой роли — действует встроенная матрица | Проверьте, что роль существует в «Управлении ролями» (раздел 4.3) |
| Роль удалена, а участники остались без прав | Права взялись из встроенной матрицы | Снимайте участников с удаляемой роли до её удаления |
| Не создаётся пользователь с нужным email | Такой адрес уже занят | Поиск в «Управлении пользователями» |

### 11.5 Развёртывание и сервер

| Симптом | Вероятная причина | Что проверить |
|---|---|---|
| Не открывается страница документации | Сервер не запущен или порт закрыт | Адрес сервера на порту 8000; состояние контейнера |
| Ошибка подключения к базе | Неверная строка подключения или база недоступна | Переменная подключения к базе; состояние контейнера базы |
| Ошибка обращения к Redis | Redis не запущен или неверный адрес | Переменные Redis; состояние контейнера Redis |
| «Таблицы не существуют» | Миграции не применены | Выполнить команду миграции из раздела 9.4 |
| Сервер стартует с неожиданными настройками | Переменные не прочитаны: опечатка в имени или регистре либо файл не в рабочем каталоге | Имена переменных с учётом регистра; рабочий каталог процесса |
| Фоновые задачи не выполняются | Запущен отдельный работник очереди задач, а процесс сервера не перезапущен | Фоновые циклы живут внутри процесса сервера; перезапустите именно его |
| Руководства не открываются по адресу документации | Отдача руководств выключена по умолчанию | Переменная включения отдачи; включать только внутри защищённого контура |

## 12. Известные ограничения

Честный перечень того, чего в системе нет или что работает не полностью.

### 12.1 Администрирование

| Ограничение | Следствие |
|---|---|
| Нет журнала действий администраторов | Нельзя узнать, кто и когда выдал права, заблокировал пользователя, изменил лимиты или роли. Для настроек моделей сохраняются только автор и время последнего изменения |
| Настройки хранилища хранят автора, но не показывают его | Кто изменил лимиты и срок хранения, из интерфейса не узнать |
| Нет истории изменений настроек | Видно только текущее значение и, для моделей, автора последнего изменения |
| Права управления метками и тегами выдаются, но меток в системе нет | Ни модели, ни интерфейса, ни правил работы с метками не существует |
| Право управления правилами проекта нельзя выдать | Его нет и в списке прав панели, и в самой системе |
| Список пользователей ограничен сотней записей без постраничной навигации | На больших системах полный список без поиска не отображается |
| Удаление учётной записи не удаляет проекты, которыми она владела | Проект остаётся без владельца, способного им управлять |
| Смена роли участника в обычном окне участников не работает | Работает только админский путь (раздел 5.4) |

### 12.2 Безопасность

| Ограничение | Следствие |
|---|---|
| Диагностические запросы моделей доступны без проверки прав | Раскрываются сведения о файлах модели, памяти и порогах; закройте маршруты на прокси (раздел 6.6) |
| Кросс-доменные запросы разрешены с любого адреса | Риск при работе из браузера с внешними адресами; ограничьте на уровне прокси |
| Пароль первого администратора не настраивается | Учётные данные известны заранее; смена пароля после первого входа обязательна |
| Связка ключей безопасности | Смена ключа шифрования или ключа подписи после сохранения токенов Git ломает их; задавайте оба явно и заранее |
| Руководство с секретами по умолчанию не отдаётся сервером | Осознанное ограничение; включать отдачу только в защищённом контуре |

### 12.3 Функциональность

| Ограничение | Следствие |
|---|---|
| Восстановление пароля не реализовано | Пользователь, забывший пароль, восстановить его сам не может; единственный путь — администратор задаёт новый пароль через карточку пользователя |
| Истёкший срок хранения корзины означает необратимость | Восстановить удалённое вложение нельзя; очистку запускайте осознанно |
| Счётчик расхода проекта обновляется при очистке | Между удалением вложения и очисткой корзины квота выглядит занятой, хотя файл уже никем не используется |
| Фоновая очистка неприкреплённых файлов отключается вместе с автоочисткой корзины | Такие файлы начинают копиться; очищайте корзину вручную |
| Интервал фоновой сверки не настраивается через файл настроек | Фактический интервал — 5 минут; требуется правка кода |
| Часть моделей требует тяжёлых зависимостей, не входящих в стандартную установку | Без дополнительной установки образ работает, но модели недоступны |
| Справочная сводка по системе не показывается в интерфейсе | Общее число пользователей, проектов и задач доступно только прямым запросом |
